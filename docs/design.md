# 设计思路

这份文档回答三个问题：**为什么这么做**、**具体怎么实现的**、**哪里还能改 / 能开出什么分支**。

## 1. 问题定义

让一个 agent「读视频」，本质是**把视频拆成它本来就能处理的模态**：

| 视频里的信息 | 载在什么上 | 拆成什么 | 用什么拆 |
|---|---|---|---|
| 说了什么 | 音轨 | 文本（带时间轴） | ASR |
| 写了什么 | 画面像素 | 静态图像 | 抽帧 |
| 是什么视频 | 页面 / 容器 | 标题、时长、编码 | 元数据 |

所以这不是"做一个播放器"，而是**一条降维流水线**：视频 → 文本 + 图像 + 元数据。

## 2. 三个硬约束，直接决定了架构

**约束一：模型看不完连续视频。**
视觉输入是"几张图"，不是"一段视频"。所以画面只能是**采样**——这决定了 `frames` 是按时间点取帧，而不是生成视频理解结果。
采样的代价是明确的：1 秒闪过的字幕会漏。要在文档里写明，而不是假装没有。

**约束二：语音必须先变成文字。**
没有哪条路能绕开 ASR。选型上，本地 faster-whisper 的 `small` 是精度/速度/体积的甜点：
461 MB、CPU int8 下约 5 倍实时、中文口播够用。

**约束三：平台的墙比技术难。**
抖音网页版的媒体是音视频分离 + 签名直链 + 有时效，`yt-dlp` 走 cookie 路线会在未登录时直接失败。
这决定了"获取层"必须能处理**用户自己从浏览器里拿到的 URL**，而不是固定一个提取器。

## 3. 分层实现

```
        ┌──────────────────────────────────────────┐
        │  cli.py     rv probe|frames|transcribe    │  ← 唯一入口，5 个子命令
        │             rv fetch|model                │
        └───────┬───────────────┬──────────────────┘
                │               │
      ┌─────────▼──────┐  ┌─────▼──────────┐
      │  media.py      │  │  asr.py        │
      │  urllib 下载    │  │  ffmpeg→f32le  │
      │  ffprobe 探测   │  │  →numpy→whisper│
      │  ffmpeg 抽帧    │  │  →txt/srt      │
      └─────────┬──────┘  └─────┬──────────┘
                │               │
      ┌─────────▼───────────────▼──────────┐
      │  models.py  本地快照优先 / hub 兜底  │
      └────────────────────────────────────┘
```

### 获取层 `media.py`

- **HTTP 用标准库 `urllib`**，不引 `requests`。理由：下载是"一个 GET + 写文件"，不值得多一个依赖树。
- **远程抽帧用 ffmpeg 的 range 请求**，而不是先下整片。552 秒的 1440p 视频，整片两百多 MB；抽 4 帧只需要几百 KB。
- **必须带 `Referer` + 浏览器 UA**：CDN 的签名校验常把 Referer 也算进去，不带就是 403。
- **`_tool()` 统一找二进制**：`RV_FFMPEG` / `RV_FFPROBE` 环境变量可覆盖，找不到时给出可操作的报错而不是 `FileNotFoundError`。

### 转写层 `asr.py`

关键决策：**音频先用 ffmpeg 解码成 `f32le`，再用 `numpy` 读进内存，最后喂给模型**。

```
任何格式 → ffmpeg -f f32le -ar 16000 -ac 1 → np.fromfile(float32) → WhisperModel.transcribe(array)
```

这条路径带来了三个好处：

1. **绕开 `av`**。faster-whisper 1.x 会调 `av.open(..., metadata_errors=...)`，旧 `av` wheel 没这个参数 → `TypeError`。我们根本不进那段代码。
2. **省掉 C 扩展安装的坑**。Windows 上 `av` 的 wheel 经常和 Python 版本对不上。
3. **格式无所谓**。ffmpeg 能解的，它就能转。

`fmt_timestamp` 用**整毫秒分解**而不是"秒 + 毫秒拼接"，因为后者在 `59.9996s` 这种边界会输出 `00:00:60,000`（这个 bug 是写测试时才发现的）。

### 模型层 `models.py`

优先级：**显式参数 > `READ_VIDEO_MODEL` > `small`（在线拉）**。

本地目录优先不是洁癖：
- 可复现（同一台机器永远用同一个模型）
- 离线可用
- 避开 hub 抖动的网络（实测官方 API 会 502，`snapshot_download` 的续传+重试才是可靠路径）

### 接口层 `cli.py`

5 个子命令，各自单一职责，错误统一收敛成 `MediaError` → 一行可操作提示。
没有 `--json`、没有插件系统、没有交互模式：**这个工具只需要能被脚本调用**。

## 4. 关键取舍

| 决策 | 备选 | 为什么选这个 |
|---|---|---|
| 抽帧采样 | 逐帧 / 光流 / VLM 直接看视频 | 只有采样在通用硬件上可行且便宜；逐帧成本高两个数量级 |
| 本地 `small` | 云 ASR API / `medium` / `large-v3` | 零成本、离线、够用；`medium` 作为可选项保留 |
| ffmpeg 远程抽帧 | 先下载整片再抽 | 省 99% 的流量与时间 |
| 单 CLI | 常驻服务 / MCP server / 库 API | 先把"能跑通"做扎实；MCP 化是明确的分支方向（见 §6） |
| Python | PowerShell / Node | 跨平台、生态（faster-whisper 是 Python）、CI 好写 |
| 不内置 `yt-dlp` | 内置一个万能下载器 | `yt-dlp` 自己已经很成熟；重复实现只会引入维护负担 |

## 5. 效果证据

246 秒中文视频，CPU int8 / 8 线程：

| 指标 | 数值 |
|---|---|
| 转写耗时 | 50.1 秒（≈ 5× 实时） |
| 抽帧耗时 | 0.2 秒 / 帧 |
| 输出 | 101 段 / 819 字 + SRT |

与画面硬字幕的时刻对齐率（人工抽查 3 处）：3/3 命中，差异只在数字写法（`729` → `七二九`）。

## 6. 可以改进的方向

按"投入产出比"排序。

### P0 —— 现在就该补

| 项 | 说明 |
|---|---|
| 端到端 CI | 目前 CI 只测合成素材；可以加一个"本地 HTTP server 提供合成视频 → rv 全链路"的集成测试，不触外网 |
| 失败重试 | `fetch` 断流只报错不重试；加 3 次指数退避（CDN 抖动很常见） |
| 并发抽帧 | 现在是串行，4 帧 0.8 秒；换成 `ThreadPoolExecutor` 能到 0.3 秒级（收益小，属于打磨） |
| `--json` 输出 | 给脚本调用方一个结构化结果，而不是解析 stdout |
| 字节进度条 | `fetch` 现在没进度，大文件像卡住 |

### P1 —— 有明显的使用价值

| 项 | 说明 |
|---|---|
| 说话人分离 | `pyannote` / `whisperx`，把"谁在说"标出来。访谈、会议、多人对话必须有 |
| 字幕强制对齐 | 用 `stable-ts` 把已有字幕轨/文稿对齐到音频，比纯 ASR 准得多 |
| 批量模式 | `rv transcribe *.m4a` / 目录递归，产物按文件名落盘 |
| 关键词高亮 | 从热词表反查命中片段，直接给"哪些时间段提到了 X" |
| GPU 自动探测 | 有 CUDA 就 `float16`，没有就 `int8`，省掉手动参数 |

### P2 —— 拓展边界

| 项 | 说明 |
|---|---|
| B站 / YouTube 适配 | 字幕轨优先（有 CC 就别转写），无字幕再落 ASR |
| 画面文字结构化 | 抽帧后接 OCR（PaddleOCR / 云 OCR），把"画面里的字"变成可检索文本，而不是靠人眼看图 |
| 评论 / 弹幕 | 抖音、B站的评论区是重要的语义补充 |
| 章节切分 | 按静音段 + 话题漂移把长视频切成章节，摘要质量会明显提升 |

## 7. 可以开的分支

每条都是独立方向，不是"以后再说"的空话 —— 改动点和成本都写清楚了。

### 分支 A：MCP server 版 —— `read-video-mcp`

把 `rv` 的四个能力包成 MCP 工具，agent 直接调用，不用 shell 出去。

- **适用**：Claude Code / Codex / DeepSeek Harness 这类支持 MCP 的宿主
- **改动**：新增 `mcp_server.py`（约 150 行，用官方 SDK），把 `media.*` / `asr.*` 注册成工具；CLI 保持不变
- **成本**：低（核心逻辑完全复用）
- **风险**：MCP 工具是同步调用，转写 5 分钟会让工具调用超时 —— 需要"任务队列 + 轮询"设计，这是主要工作量

### 分支 B：纯视觉版 —— `read-video-vision`

不转写，只抽帧 + 让视觉模型描述，适合无台词/音乐类视频。

- **适用**：纯音乐 MV、无对白动作片、需要理解画面构图的场景
- **改动**：去掉 `asr.py`，加 `describe.py`（调多模态 API）；抽帧改成关键帧检测（画面差异阈值）而不是固定间隔
- **成本**：中（关键帧算法是新的）
- **依赖**：需要视觉模型的 API key，不再是纯本地

### 分支 C：字幕工厂版 —— `read-video-subtitle`

面向"给视频加字幕"的生产场景，而不是"给我读内容"。

- **适用**：搬运、二创、多语言发布
- **改动**：`transcribe` 加 `--burn`（ffmpeg `subtitles=` 滤镜烧录）、`--translate`（接翻译 API）、双语 SRT 输出
- **成本**：低（ffmpeg 能力现成）
- **注意**：烧录会重编码，耗时和画质损失要写清楚

### 分支 D：中文强化版 —— `read-video-zh`

把 whisper 换成 SenseVoice / FunASR。

- **适用**：纯中文内容、带方言（粤语）、需要情感/事件标注
- **改动**：`asr.py` 抽出 `Engine` 接口，加 `SenseVoiceEngine` 实现；模型下载走 ModelScope 而不是 HF（国内更快）
- **成本**：中（两种引擎的输入输出契约不同，VAD 行为也不同）
- **收益**：中文准确率通常优于 whisper `small`，尤其专有名词

### 分支 E：零安装版 —— `read-video-wasm`

浏览器内跑 whisper.cpp（WASM），配合 Playwright 抓流，全程不落地文件。

- **适用**：不想装 Python/ffmpeg 的用户、一次性使用
- **改动**：几乎重写（前端 + WebAudio + wasm 模型）
- **成本**：高
- **收益**：门槛降到"打开一个网页"

## 8. 一条经验

这个项目 90% 的时间花在**和环境搏斗**，不是算法：

- curl 在这台机器上 TLS 全挂（`status 000`），只能换 .NET / urllib
- 同一条 URL，裸 ffmpeg 能下、Python subprocess 却报证书错误（TLS 中间人）
- PowerShell 5.1 按 GBK 读无 BOM 的脚本，中文注释直接把语法读崩
- 抖音的登录弹窗会周期性重弹，浏览器截图永远截到二维码

所以真正可复用的资产不是代码，是这些**踩坑记录**（`SKILL.md` 的坑表、`docs/douyin.md`）。
这也是为什么文档和测试的地位和代码一样高。
